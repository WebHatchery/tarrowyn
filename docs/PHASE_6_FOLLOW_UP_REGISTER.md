# Phase 6 follow-up register

This register keeps release-candidate evidence separate from work that needs a
deployment environment, a later product decision, or more content. It is the
short list to review before expanding Tarrowyn beyond the supported regional
preview.

| Work item | Status | Evidence in this repository | Exit evidence still required |
|---|---|---|---|
| Target MySQL migration and restore | Target-required | `scripts/verify_mysql.ps1` contains the migration, restart, replay, backup, concurrency, and native dump/restore assertions. The ignored preview file now uses the documented `DB_USERNAME` key, and a password-safe `SELECT 1` succeeds. `SHOW GRANTS` confirms the account has `ALL PRIVILEGES` on the configured `tarrowyn` schema, but no server-level `CREATE` or `DROP` grant. The focused acceptance run reached the worker readiness check but the existing database failed closed with `production` integrity because legacy refresh replay results have no ownership mirror in the current snapshot; no persistence assertion was claimed. The verifier now probes disposable-schema privileges before starting the server; that probe returns MySQL `ERROR 1044` for the configured account, so no schema or data was changed. Local JSON failure injection also proves mutation writes return `503 persistence_unavailable` and restore the last durable state; this does not replace live MySQL evidence. | Grant the acceptance runner `CREATE/DROP DATABASE` permission and provide a clean, current preview snapshot without deleting the configured database as part of this task, run the full script, then have the deployment owner repeat the same checks against the target database, including a known-good restore and integrity comparison. |
| Authoritative server deployment artifact | Target-required | `tarrowyn-server` is source-built by the documented local and acceptance runbooks, while the release gate now seals the Windows/WebGL client archives with commit-addressed manifests and rollback evidence. | Browser API origin and online bootstrap | Target-required | A fresh Chrome check of `https://webhatchery.au/games/tarrowyn/` renders the published WASM page and remains free of the deleted-texture warning, but its console shows repeated failed requests because the checked-in `gateway_url` is intentionally blank and the browser artifact falls back to `http://127.0.0.1:8787`; static WASM cannot consume `TARROWYN_SERVER_URL` at runtime. The project-local `register-server.ps1` provides the same heartbeat shape as the established gateway client, but no `tarrowyn` gateway service is provisioned here; on 2026-08-31, direct GET checks of both the gateway health route and `.../api/p/tarrowyn/health` returned LiteSpeed HTTP 404. | Multi-worker and regional handoff | Target-required | The MySQL bridge holds one process-lifetime world-authority lock; a second worker fails closed. | Deployment identity, TLS, and secrets | Target-required | The OIDC link/refresh/revoke fixture, secret-free account view, and client session recovery are covered locally. | Configure the real identity gateway, TLS termination, secret manager, rotation, credential recovery/MFA boundary, and external alert routing in the target environment. |
| Scale beyond the supported regional target | Target-required | The region worker now serves requests through a bounded 4-to-32-worker HTTP pool and a queue configurable from 16 to 4096 requests, defaulting to 128. The MySQL bridge reserves one authority-lock connection and bounds its shared pool maximum to 2–32 connections, defaulting to 4; authenticated operator metrics expose that effective maximum, while JSON fixture workers report zero. Guest admission keeps a secure default burst of 32 attempts per source, while the controlled load harness configures the requested bootstrap bound. Operator metrics expose effective worker count, queue capacity, active requests, current and peak queue depth, and queue-full events. The 24-client mixed-load drill passes and reports 16 workers, a 128-request queue, queue peak 1, and 0 full events. Post-pool 50-, 100-, and 250-client one-round runs completed with 500 requests in 9,177.11 ms, 1,000 requests in 19,358.17 ms, and 2,500 requests in 97,107.35 ms, respectively. They measured 62.61 MB, 64.79 MB, and 76.58 MB working sets, with 2,795.53 ms, 2,744.26 ms, and 2,780.21 ms restart recovery; the first two runs had only the explicitly allowed `market_backlog` alert and the 250-client run had no operational alerts. A repeat telemetry boundary run also reported 16 workers, a 92/128 queue peak, and 0 queue-full events with no operational alerts, while measuring 101,053.55 ms mixed-load time, 75.75 MB working set, and 13,064.87 ms restart recovery. These remain monitored capacity evidence, not a capacity claim. | Select topology and establish target-environment limits for concurrency, latency, memory, tick drift, queue pressure, database connections, and restart recovery. Prove that the worker pool remains stable under the target several-hundred-client workload. |

The register does not authorize a public launch by itself. The target-required
rows remain deployment gates; the deliberately deferred rows remain product
choices rather than missing implementation. Any new row should name its owner,
evidence, and exit condition before code or content is added.
