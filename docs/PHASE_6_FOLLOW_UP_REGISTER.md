# Phase 6 follow-up register

This register keeps release-candidate evidence separate from work that needs a
deployment environment, a later product decision, or more content. It is the
short list to review before expanding Tarrowyn beyond the supported regional
preview.

| Work item | Status | Evidence in this repository | Exit evidence still required |
|---|---|---|---|
| Target MySQL migration and restore | Target-required | `scripts/verify_mysql.ps1` contains the migration, restart, replay, backup, concurrency, and native dump/restore assertions. The ignored preview file now uses the documented `DB_USERNAME` key, and a password-safe `SELECT 1` succeeds. `SHOW GRANTS` confirms the account has `ALL PRIVILEGES` on the configured `tarrowyn` schema, but no server-level `CREATE` or `DROP` grant. The focused acceptance run reached the worker readiness check but the existing database failed closed with `production` integrity because legacy refresh replay results have no ownership mirror in the current snapshot; no persistence assertion was claimed. The verifier now probes disposable-schema privileges before starting the server; that probe returns MySQL `ERROR 1044` for the configured account, so no schema or data was changed. | Grant the acceptance runner `CREATE/DROP DATABASE` permission and provide a clean, current preview snapshot without deleting the configured database as part of this task, run the full script, then have the deployment owner repeat the same checks against the target database, including a known-good restore and integrity comparison. |
| Multi-worker and regional handoff | Target-required | The MySQL bridge holds one process-lifetime world-authority lock; a second worker fails closed. Client cursors are recoverable, but ownership handoff is not implemented. | Choose relational ownership and cursor handoff, then prove node/region failure without duplicate rewards, split-brain state, impossible travel, or cursor gaps. |
| Deployment identity, TLS, and secrets | Target-required | The OIDC link/refresh/revoke fixture, secret-free account view, and client session recovery are covered locally. | Configure the real identity gateway, TLS termination, secret manager, rotation, credential recovery/MFA boundary, and external alert routing in the target environment. |
| Scale beyond the supported regional target | Target-required | The 24-client mixed-load drill passes. Exploratory 50/100/250-client runs are retained as monitored capacity evidence, not a capacity claim. | Select topology and establish target-environment limits for concurrency, latency, memory, tick drift, queue pressure, and restart recovery. |
| Richer route and market inspection | Implemented surface | The online sidebar keeps compact authoritative road availability/risk, open orders, and the protected-law boundary, while the visible `Inspect` control opens route names/status/condition/risk, the first stock and price notes, and the latest event's cause, exact touch-selectable choices, and outcome state from the same server projections. | Playtest the detail wording and information density; adjust the surface if player evidence shows that detail competes with recovery, comparison, or chronicle controls. |
| Player-facing chronicle archive search | Partial client surface | The Chronicle panel now submits the visible query value to the authenticated `/v1/chronicle/search` endpoint, shows bounded returned records and archive range, lets a player run an all-history search with the visible Search control, and advances a full result page with a visible Next control. Free-form query text is accepted while the panel is open and the server response remains authoritative. | Add true touch text entry for arbitrary queries and focused client/server fixtures for that path without hiding recovery or regional controls. |
| Season and year pacing | Deliberately deferred | The 80-minute day is locked; the four-season, 14-day season and 56-day year values are development fixtures. The long-session test crosses boundaries without locking access. | Run player-facing crop, lease, access, and economy playtests; record the final calendar decision before seasonal timing becomes a product promise. |
| Content expansion and support cadence | Post-launch content work | The manifest gate and typed server validators protect IDs, required fields, cross-references, fallback services, and newcomer access. | Add content in small reviewed batches, attach compatibility fixtures, and monitor population, scarcity, abandoned claims, settlement decline, and newcomer access after each batch. |
| Existing saved-world farm layout migration | Follow-up before persisted topology edits | Fresh worlds use the validated region manifest, and the known empty legacy six-plot layout upgrades safely to the current three plots; populated or unknown layouts remain stored so crops are not silently moved or discarded. | Before changing launch plot positions or count in a persisted world, add a versioned migration that preserves crop state and defines the policy for removed plots, then repeat restart, backup, and restore acceptance. |
| Storm Magic merger interaction path | Implemented surface | The severe-weather Spell control now records one three-element working per encounter after mastered Wind, Water, and Electricity Magic; 25 persisted interactions reveal Storm Magic, and the same touch control becomes its one-use combat technique. | Playtest interaction pacing, discovery feedback, storm damage, and weather availability before promoting the merger beyond the regional preview. |
| Human regional playthrough | Evidence still desired | Automated three-client, Phase 4, Phase 5, MySQL, failure, and long-session checks cover the current release candidate. | Record a human multi-session regional playthrough when the client is available for that study; treat it as product evidence, not a substitute for server acceptance tests. |
| PvP, criminal roles, generational play, and general NPC life simulation | Deliberately deferred | The GDD protects the launch law boundary, immortal characters, and fixed authored NPCs. | Reopen each system only with a separate design decision, migration plan, recovery rules, and acceptance fixtures. |

The register does not authorize a public launch by itself. The target-required
rows remain deployment gates; the deliberately deferred rows remain product
choices rather than missing implementation. Any new row should name its owner,
evidence, and exit condition before code or content is added.
